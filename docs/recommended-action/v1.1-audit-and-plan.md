# Recommended Action V1.1 (`nba-v1.1.0`): audit and plan

Answer to the kickoff in `Obsidian_Gallery_Recommended_Action_V1_Refinement_Claude.md`. Nothing here is
implemented yet; it needs owner sign-off (section 6). Written 2026-11-02 from the working tree and the live
Supabase schema (read through the REST schema, not the database).

## 0. One mismatch that changes the plan

The spec says V1 is "already deployed on real user data". It is not. Phases 1–2 run only on localhost:
nothing is committed, and `RECOMMENDED_ACTION_ENABLED` is set only in `.env.local`. The three tables exist in
production (the migration was applied), but they hold only the test rows from the owner's localhost session.

Consequences:
- There is no production V1 baseline, so **shadow-comparing against the old band ranking has nothing to
  compare to.** Proposal: v1.1 becomes the first ranking anyone sees. Replace shadow mode with a read-only
  review script that prints the top 3, with reasons, for 10–20 real accounts.
- Canary percentages are meaningless at this size. Proposal: allowlist (owner, then a handful of users), then
  everyone. `RECOMMENDED_ACTION_USER_IDS` already exists.
- Keeping existing identities is free: keys and suppression rows don't change.

## 2. Why RA03 wins, and the smallest safe fix

`engine.ts` `compareCandidates` sorts by `effectiveBand` **before** score. RA03 is always band 1
(Activation) and every unit-work rule is band 3. So any project with `unitCount === 0` beats every RA09 and
RA07 candidate, whatever the score, for every user. Scores never meet. "Test project" also gets the top
sub-sort because it was the empty project with the newest `updated_at`.

**Smallest safe fix (one rule, no schema change):** RA03 is eligible only when one of these holds:
- the user has no units at all (not activated), or
- the project was created in the last 14 days, or
- the project is featured (the user's explicit choice).

Otherwise RA03 is rejected with reason `lifecycle_gate`. Add a regression test for the owner's case:
established painter with active units, sessions this week and a 60-day-old empty project, where RA03 must not
appear in the top 3. Bump the ruleset to `ra-2026-11-02.1`. About 20 lines plus a test. Keys stay the same.

## 3. Data model: lifecycle, intent, momentum

### One new read path: an RPC, not N queries

`recommended_action_activity()` is `security invoker`, so RLS still applies and `auth.uid()` is the only
user it can see. It returns one JSON object per call:

- **User:** `firstMeaningfulAt`, `lastMeaningfulAt`, meaningful days and action counts for 7 and 30 days, and
  per-family counts for 30 days (painting, paint_collection, guide_creation, guide_discovery).
- **Per unit** (the units below): last meaningful activity, sessions in 7/30 days, total session minutes in
  30 days, last photo, palette and guide-attachment counts.
- **Per project** (≤50): last child activity (unit added, or a session or photo on any of its units),
  child unit count.
- **Per draft guide:** last content edit (`max(guides.updated_at, recipe_steps.updated_at)`), card count.

A "meaningful action" means:
- a painting session that ended with at least `MIN_SESSION_MINUTES` (proposal: 5), a unit photo, a unit
  created, a stage change (once dateable), or a palette or guide attached;
- a guide card edited;
- a paint marked owned.

Project creation alone, page views and PostHog events don't count.

**Unit window fix:** load the 40 most recent by `updated_at`, **plus** featured units, units with a session
in the last 30 days, and `status = 'active'` units, capped at 80. Report `snapshotCoverage`: truncated or
complete.

**Cost:** about six grouped aggregates over one user's rows, each filtered by `user_id` plus a date. Needs
indexes on `unit_sessions(user_id, started_at)`, `image_assets(user_id, entity_type, created_at)` and
`unit_projects(user_id, created_at)` (I'll check which exist before the migration). The aggregates should run
in a few ms at today's row counts. It's one extra round trip, run in parallel with the existing first round.

### The one necessary schema addition

`unit_progress_steps.updated_at` with a `before update` trigger. Without it, "stage changed recently" can't be
dated, and spec rules for RA07 ("trustworthy subsequent activity") and momentum can't use stage changes.
History before the migration has no date: those rows count as unknown (low confidence), never as recent.

### Classifiers (pure functions in `lib/recommended-action/context.ts`)

- `classifyLifecycle`: new / activated / established / lapsed, with the spec's thresholds as config. Live
  running session overrides. Confidence is `low` when the unit window was truncated or stage history is
  undated.
- `inferIntent`: per-family evidence score (count, unique days, a 7-day recency boost). The onboarding goal is
  a prior that is strong while new and fades with evidence. `mixed` when two families are strong.
- `familyFamiliarity`: never_tried / tried_once / repeated, per family, from the same counts.
- `targetMomentum`: the spec's 0–3 / 4–7 / 8–14 / 15–30 day curve plus action count, capped at 45 when only
  generic timestamps exist.
- `abandonmentRisk(project)`: the spec's points table. A provisional name is worth +10 at most, featured is
  −50, recent child activity is −50.

| `lib/recommended-action/engine.ts` | Bands replaced by **protected tier** (running session, RA10 ≤48 h, just-created flow) + one score; spec weights; itemized penalties; `qualityAdjustment` stub fixed at 0; full trace in `diagnostics` |
| `lib/recommended-action/config.ts` | Ruleset `nba-v1.1.0`; all thresholds and weights in one object |

| `app/api/recommended-action/events/route.ts` | Accept the new event types and an optional dismiss reason |
| `app/dashboard/recommended-action-card.tsx` | Send `action_failed` when the destination can't resolve; optional dismiss reason (decision 3) |
| `scripts/recommended-action-review.mjs` (new) | Read-only: top 3 + reasons for a list of user ids, printed locally; no content to analytics |
| `scripts/recommended-action-weekly-report.mjs` (new) | Spec §11 table from the events tables: raw counts, unique users, "insufficient evidence" labels |
| `tests/recommended-action-v1-1.test.ts` (new) | S1–S15 fixtures; existing 37 tests keep passing |

**Risks**
- *Authorization:* the RPC must be `security invoker` and take no user id parameter. The traces table needs
  owner-only RLS.
- *Performance:* one extra parallel query. Measure before and after against the existing ~server-loading
  budget.
- *Compatibility:* keys unchanged. Existing dismiss and snooze rows apply as-is. Rollback means setting the
  ruleset config back; there are no data migrations to undo, and the new column and RPC are additive.
- *Spec scenarios for unbuilt rules:* S8 (RA16) and S9 (RA14) can only be tested negatively (RA13 "start
  collection" must not win for a collector) until those rules exist.

## 5. Test-driven sequence

1. **RA03 gate** (section 2): test first, then the fix. Can ship on its own.
2. **Context:** migration (column, trigger, RPC, indexes) → snapshot additions → classifier unit tests
   (lifecycle edges, intent prior fading, abandonment points, the low-confidence path for undated stages).
3. **Ranking:** replace bands with protected tier + single score → S1–S7, S10–S15 fixtures. Each asserts
   winner, top alternatives, *must-never* invariants and the reason trace.
4. **Event quality:** new event types, `action_failed`, `evaluation_fault`, invalidation, traces.
5. **Review and report:** review script on 10–20 real accounts (owner reads the output), weekly report.
   `qualityAdjustment` stays 0 behind a flag.
6. **Rollout:** owner allowlist → a few users → everyone, with guardrail checks from the weekly report (stale
   RA03 exposures = 0, start-session while a timer runs = 0, `action_failed` rate).

The card restyle from today is independent and can be committed with step 1.
